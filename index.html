Welcome to the technical portion. Let's begin with a system design scenario.

You are tasked with designing a highly available, global URL shortener service (similar to Bitly). The system needs to handle 10,000 URL creations per second and 100,000 redirects per second.

Walk me through your high-level architecture, specifically focusing on the database choice and how you would handle scaling the redirect reads.

InterviewAI • 10:02 AM
person

For a read-heavy system like a URL shortener with a 10:1 read-to-write ratio, my primary focus would be on minimizing read latency and handling high throughput.

I'd start with a load balancer distributing requests to stateless API servers. For the database, a NoSQL solution like Cassandra or DynamoDB is ideal here because the data model is simple (Key: short URL, Value: long URL) and we need massive horizontal scalability and high availability.

To handle the 100k redirects/sec, caching is critical. I'd implement a distributed cache like Redis or Memcached in front of the database. We can cache the most frequently accessed URLs. A Cache-Aside pattern would work well here.
